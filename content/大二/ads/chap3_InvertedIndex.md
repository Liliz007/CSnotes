# 1.Intro

如何快速地找到在哪些文档中包含了我们想要查询的关键词？

## 1.1 暴力扫描法

直接在所有页面中扫描所需关键词。

- 缺陷：太慢了，不可接受

## 1.2 词汇-文档关联矩阵（词袋模型）

**构建方式：**
把所有文档中出现过的所有词提取出来，作为矩阵的行；
把所有文档的编号作为矩阵的列。如果一个词在某篇file中出现，则将对应格记为1，没出现过为0.

**示例**
![](../image/2026-01-03-21-32-33.png)

现在，如果我们想查询包含 silver 并且 truck 的文档，该怎么做？
1. 找到silver对应的行向量[1,0,1,0]
2. 找到truck对应的行向量[1,0,1,1]
3. 按位与，得到[1,0,1,0].这俩1就是所要找的files

**优点：**
- 逻辑清晰，快，好写
- 支持多关键词查询：做按位与运算。（如图中例子

**缺点：**
* 太稀疏了。英语词汇量几十万，网页数量千亿，太大太多0
* 难以扩展，每增加一个新term或新file，都要给这个巨大矩阵增加一行或一列。
* 空间复杂度：$O(|V|*|D|)$，|V|是总词汇数，|D|是文档总数。

所以，词项-文档矩阵虽然在思路上进了一步，但依然不实用。我们需要一种**只存储“有效信息”（也就是那些 1 的位置）**的数据结构。

# 2.倒排索引(Inverted File Index)

它的核心思想非常简单：我们不记录词在哪个文档中“没有出现”，**只记录它“在哪里出现了”**。

## 2.1 定义

1. 索引(Index)：用于**快速定位**文本中**给定词项**的机制
2. 倒排索引：它包含了一个从**词项**(Term)到其出现位置的**指针列表**的映射。这个“位置”通常是指向文档的ID。

>之所以称为“倒排”，是因为它颠倒了“文档 -> 词项”的自然关系，变成了“词项 -> 文档”。

**倒排索引的组成**
1. 词典(Dictionary):包含了系统中全部词
2. 倒排列表(Posting List):对于词典(Dic)中每个词项，都有一个对应的列表。此列表记录了包含该词项的所有files的ID

对于上例，我们可以构建这样的倒排索引：

![](../image/2026-01-03-21-56-33.png)

这样我们再来处理silver和truck的查询：
1. 在Dic中找到silver，获取其倒排列表[1,3]
2. 找到truck，[1，3，4]
3. 求列表交集，得到[1,3]。

## 2.2 扩展倒排索引：不止记录是否出现

我们想知道更多信息：
1. 词频Frequency
2. 具体在文档中的哪个位置？Position
3. 如何根据相关性对检索结果排序？（搜索的重要一环

![](../image/2026-01-03-22-02-42.png)

解释：<3; (2;6),(3;6),(4;6)>表示
* a总共出现了3次(Times)
* 出现在第2篇的第6个
* 出现在第3篇的第6个
* 出现在第4篇的第6个

## 2.3 倒排索引的构建

从原始文档集合构建它。

```c
// 初始化一个空的倒排索引
InvertedIndex index = new InvertedIndex();
//注意倒排索引包含：1.词典；2.倒排列表（词到位置的指针表合集）
while (还有未处理的文档 D) {
    // 读取一篇文档
    document D = read_a_document();
    
    // 对文档进行分词
    tokens = tokenize(D.content);
    
    while (tokens 中还有词项 T) {
        // 读取一个词项
        term T = read_a_term(tokens);
        
        // 查找词典中是否已有该词
        if ( !index.dictionary.contains(T) ) {
            // 如果没有，添加到词典，并创建一个新的倒排列表
            index.dictionary.add(T);
            index.postings.add(new PostingList());
        }
        
        // 词典中已有该词。获取该词项的倒排列表
        PostingList posting_list = index.get_posting_list(T);
        
        // 将词T在当前文档D中信息（ID, 频率, 位置）添加到它已有的倒排列表中
        posting_list.add_node(D.ID, ...);
    }
}
// 将构建好的索引写入磁盘
write_index_to_disk(index);
```

### 文本预处理

1. 词干提取(word stemming)：直接把后缀砍掉；
2. 词形还原(Lemmatization)：更精细的方法，将不规则的变形还原。如said->say
3. 停用词(stop word)：如a,the,in等。

### 数据结构的选择

讨论存储词典所用的数据结构。Hashing和搜索树的pros and cons？

1. 哈希表：
   * 优点：速度快
   * 缺点：
     * 不支持范围查询
     * 为降低冲突率，需要预留更多空间
     * 处理冲突有额外开销
2. 搜索树：
   * 优点：
     * 有序性：支持范围查询、前缀查询
     * 性能稳定：最坏情况也是$O(logN)$.不像hash，最坏时全部冲突，复杂度为$O(N)$

# 3. 海量数据：扩展性设计

## 3.1 内存不足：SPIMI

当文档集合非常大，以至于**无法在内存中一次性构建整个倒排索引**时，我们怎么办？

SPIMI：Single-Pass In-Memory Indexing，单趟在内存排序

```c
//分块建倒排索引
BlockCnt = 0; 
while ( read a document D ) 
{
  while ( read a term T in D ) 
  {
    //内存满了
    if ( out of memory ) 
    {
      //省略了一段内容：对索引块按词项进行字母序排序
      //把当前块的倒排索引（词典+倒排列表）写回disk
      Write BlockIndex[BlockCnt] to disk;
      //下一块
      BlockCnt ++;
      //清空内存
      FreeMemory;
    }
    //处理当前块
    if ( Find( Dictionary, T ) == false )
      Insert( Dictionary, T );
    Get T的 posting list;
    Insert a node to T的 posting list;
  }
}

//由于索引块内部有序，因此归并是基于归并排序的。
for ( i=0; i<BlockCnt; i++ )
  Merge( InvertedIndex, BlockIndex[i] );
```

## 3.2 Web级索引：分布式索引(Distributed Indexing)

此时单台机器完全处理不了。我们想用多台机器进行分布式索引。

### 3.2.1 按词项分区(Term-partitioned)

将词典切分，放到不同的机器上，如下图

![](../image/2026-01-04-16-28-22.png)

* 查询处理：一个查询，如 "distributed indexing"，需要被分发到 "d" 所在的机器和 "i" 所在的机器，分别获取倒排列表，然后由一个聚合节点合并结果（取交集）。
* 优缺点：并发性好；扩展性有限（高频词的存储压力较大），跨节点（即在不同机器上的）的查询会增加网络开销和延迟（通信延时之类）

### 3.2.2 按文档分区(Document-partitioned)

将文档切分，每台机器负责一个子集，并为这个子集建立一个大的，完整的倒排索引。（词典包含此子集内的所有词汇）

![](../image/2026-01-04-16-37-32.png)

* 查询处理：一个查询要被广播到所有的机器上，分别对这些子集进行扫描（找到目标词项），返回局部结果后，由一个聚合节点合并所有局部结果（得到所有目标文档）。
* 优缺点：扩展性特别好，增加新文档只需增加新机器，查询时并行度高。通常被称为**分片(Sharding)**

### 3.2.3 动态索引(Dynamic Indexing)

由于互联网动态变化，网页有增有减，不可能总是重新构建倒排索引。

解决——主辅索引(Main-Auxiliary Index)

![](../image/2026-01-04-17-04-24.png)

>ps:这个人讲得好牛逼啊

* Main Index : 存在disk上，不直接接受写（修改）
* Auxiliary Index : 存在Mem中。所有新加入的file都存在辅引中
* Deletion List : 一个file被删除时，先不对disk进行物理删除（因为很慢）。对主辅索引中该文档进行删除标记——即，将该ID记录到一个“删除列表”中。

* 处理查询：
  * 用户发起查询。
  * 系统同时查询主索引和辅助索引。
  * 合并两边的结果。
  * 使用删除列表过滤掉已删除的文档。
  * 返回最终结果给用户。
* 何时re-index？
  * 当辅索引太大，或删除列表太长时，查询性能下降。
  * 触发一个merge，将辅索引中的内容合并到主索引中，并真正将删除列表中标记的文档从disk中删除。
  * 这个过程在后台进行，不影响线上服务
* 如何删除file？
  * 逻辑删除。即只标记它，物理删除等到merge时统一进行。

# 4. 性能优化

## 4.1 存储优化——Compression（索引压缩）

希望压缩倒排索引，特别是倒排列表所占用的存储空间。
* 词典压缩：对于排好序的词典，相邻的词项通常有共同的前缀。可以使用前缀编码 (Front Coding) 等技术来压缩。
* 列表压缩：一个词的倒排列表（文档ID列表）是单调递增的。可以不存原始编码，用差值存储。数值小了，占用的位数也就少了。

## 4.2 查询优化——Thresholding（阈值法）

1. 文档阈值：只计算排名前k个文档的相关性得分。（排名由更容易计算的静态质量分，如权威程度得出）
2. 词项阈值：对于一个多词查询，可以先用最稀有的2-3个词来筛选，缩小候选文档集合。再用剩下的词在这个集合中进行过滤。

## 4.3 性能衡量

1. 效率：
   * 索引速度：单位时间能处理多少files？
   * 查询速度：返回查询结果需要多长时间？
2. 表达能力：
   * 查询语言是否强大？能否支持复杂的布尔逻辑、短语查询、模糊查询？
3. 用户满意度：引入**精确率(Precision)**和**召回率(Recall)**的概念

# 5. 提升相关性——不只是“出现”

如何提升搜索结果的相关性？ 仅仅找到包含查询词的文档是远远不够的。**我们需要对结果进行排序，把最可能满足用户需求的排在最前面。**

**TF-IDF排序法**

- tf：term frequency，一篇中出现次数，能代表主题倾向

- df: document frequency，很多篇中都出现很多，表示是废词，如the等

- TF-IDF模型（tf/df）：能更好的表达文本的意义。因为某个term的主题相关性与tf成正相关，与df成负相关
  - 但如果数据集太大，df太大，tf/df总是趋于0，就没有区分度了。
  - 改进：对df取log等，将其规范化（防下溢）

- TF-IDF算法缺陷：对主谓宾顺序不敏感（如“中国打败美国”=“美国打败中国”）。
  - 改进：k-gram模型，一次看k个词。复杂度：O(n^k)，对n和k都有限制，不能太大。
